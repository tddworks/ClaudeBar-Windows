# Tools in WSL (design, 2026-11-03)

Many people on Windows run Claude Code, Codex and the rest inside WSL. Their sign-ins, logs and CLIs are in the distro's Linux home, and ClaudeBar for Windows reads only `%USERPROFILE%`, so those tools show as not set up, or not at all, and their tokens never reach the Leaderboard. This reads them where they live. Evidence: [`design-concept/wsl/research.md`](../../design-concept/wsl/research.md); the spike is on branch [`spike/wsl-probe`](https://github.com/tddworks/ClaudeBar-Windows/tree/spike/wsl-probe).

## Decisions

- **ClaudeBar itself, built for Linux, runs inside the distro:** `claudebar-probe`, from ClaudeBar's package with its Linux adapters (`LinuxProcesses`, `LinuxPty`, `{{platform.appData}}`, the time zone). Inside the distro, a tool's paths, CLI and logs are where ClaudeBar on Linux expects them, so the package needn't know about WSL, and CLIs work from the start. A `${VAR}` set only in the person's shell files isn't in the probe's environment until the probe reads it from their login shell (*The environment*).
- **Rejected: the package reads a "place" over `\\wsl.localhost`.** It needs a new parameter in the shared code, still can't run a CLI, needs SQLite copied off the 9P share, and reading the share boots a stopped distro. Nor can Windows see the distro's environment: a `CODEX_HOME` exported in `.bashrc` is in no file the share holds. The probe can, by asking the login shell inside the distro.
- **Rejected: an account per tool pointing into WSL** (`{{account.folder}}` = `\\wsl.localhost\…\.claude`). This app has no account settings, the Leaderboard reads default logins only, a CLI source would run the Windows CLI against the Linux folder, and every read boots the distro.
- **Rejected: junctions** from `%USERPROFILE%\.claude` into the distro. They break a Windows install of the same tool, boot the distro whenever anything touches the folder, and change the person's files to make a reading.
- **Only running distros are read,** from `wsl.exe -l --running -q`, which starts nothing. A stopped distro keeps its last reading, marked as such.
- **The glibc x86_64 build ships first.** The musl build needs nothing in the distro, but needs two packages patched and still hangs in a refresh (research). arm64 isn't in the first release.

## Phases

1. **The HUD, Limits and Settings for WSL, and the probe.** Builds on ClaudeBar as pinned today. The uploader sends this PC's days only, as now.
2. **WSL days on the Leaderboard.** Waits for one change in ClaudeBar (*Late days*, below) and a pin bump. The probe counts a distro's days in Windows' zone (*The time zone*), so ClaudeBar labels them as it labels this PC's, with no other change. No WSL day is sent before then, so none can shrink when it comes.

Two changes go to ClaudeBar first, as problem-first issues:

- **Late days** ([#680](https://github.com/tddworks/ClaudeBar/issues/680)), for phase 2, and a bug on the Mac today. The uploader reads from the day of `lastUpload` (`range(endingOn:within:retrying:)`, `LeaderboardUploader.swift:104-108`), and `due(_:retrying:)` (112-116) drops every day before that day but the refused ones: *not the days in between, which the server already took*. So a day that first appears, or grows, after an upload that moved past it never reaches the server, and the Mac loses days this way now (*The Leaderboard*). The change: the membership keeps what this device last sent per provider and day, and a day before the cut goes again only when its total is larger than that (*The Leaderboard*).
- **Version managers in `commonPaths`** (*PATH*), for phase 1 to find CLIs installed with nvm, Volta, fnm, mise or asdf; `Internal/Linux/Process/LinuxProcesses.swift` only. Without it those CLIs show as not set up. Landed as tddworks/ClaudeBar#683, in the pin since `7d5a61f5`.

## The probe

- **The same code as the Windows side.** `HudMonitor`, `HudReading`, `ProviderTokenLogs` and `ClaudeBarSettings` move to a target of their own, `ClaudeBarShared`, which `native/` and the probe's `linux/` package both build, at the same ClaudeBar commit. `SettingsFile` stays Windows-only (it imports `WinSDK`).
- **The launch:** `wsl.exe -d <distro> -e env CLAUDEBAR_WSL_RUN=<id> TZ=<zone> <probe> --json --windows-roots <file>`, with Windows' zone (*The time zone*). `-e` runs it as the distro's default user without a shell, so the CLIs run without the person's shell files. The probe runs the login shell once, only to write the variables the definitions name to a file of its own, with the shell's output going nowhere, so nothing the shell files print gets in the JSON (*The environment*). It reads that user's home only: tools another Linux user set up show as not set up. A per-distro user is left for later.
- **Its answer** is `ProbeReading`, one `Codable` type in `ClaudeBarShared`:
  - `hud`: the HUD's answer, `{reading, readAt, problems, looks}`, exactly what `cbw_hud_reading` returns for this PC; `null` with `--logs-only`.
  - `days`: `[DailyTokens]`, ClaudeBar's own day (`provider`, `day` as `yyyy-MM-dd`, five token counts), made in the probe by `DailyTokens.summed` with the calendar it counts in, Windows' zone; `null` when it couldn't count in that zone (*The time zone*), which Swift's coders write by leaving the key out, and read either way. The wire carries day labels, never `Date`s.
  - `tools`: each tool found and where (its CLI's path, or *logs only*); `skipped`: each source left out as shared with Windows (*Folders shared with Windows*), with its Windows path.
  - `version` (the client's), `timeZone` (the zone its days are counted in: Windows', or the distro's own when it couldn't use Windows'), `timedOut`, `environmentImport` (`imported` with the names it set, or `failed` with why; never the values), and `diagnostics` (a fallback taken, a path that couldn't be mapped, a zone refused).
- **`--deadline <s>`** (60 by default) bounds the refresh. When it passes, the probe answers with the HUD as read by then, logins still reading marked `reading`, and `timedOut: true`. The days are read after it, whole, every time. With no answer 60 s after the deadline, the probe ends its CLIs and exits 2 with nothing; a run without an answer replaces nothing.
- **Each CLI gets 30 s more to start.** WSL takes an idle distro's page cache back, so at the HUD's ten-minute cadence the CLIs start from the virtual disk: Claude showed nothing for 18–24 s and Codex's app-server answered after 11–19 s, past their 20 s and 15 s ([research](../../design-concept/wsl/research.md#cold-clis-at-the-huds-cadence-2026-11-05)). The probe binds ClaudeBar's `FetchContext.startAllowance` ([#685](https://github.com/tddworks/ClaudeBar/issues/685)) to 30 s around the refresh: a terminal CLI's timeout counts from when its screen first shows something, a JSON-RPC CLI's from its first answer, a command's grows by it. A CLI that answers at once is read as before. The app passes `--deadline 90`, 60 s and the allowance (`ProbeTiming`): a CLI that never answers is stopped only at its timeout plus the allowance, and the data source it falls back to starts then (Codex's JSON-RPC, 15 s, then its terminal), so that one keeps the 45 s it had in 60 s. The mutex wait and an update's hold on the distros cover a whole run at its longest, 240 s: two `wslpath`, the deadline, the 90 s answer window, then the running list and `--end`, 15 s each step (180 s before).
- **`--logs-only`** skips the refresh: no CLI, no pty, no network. It still reads the environment, so its days come from the folders the HUD's do. The uploader uses it, from phase 2.
- **The marker.** Killing `wsl.exe` doesn't end the Linux side, and a CLI is reparented to `init` when the probe dies, so the processes of a run are found by `CLAUDEBAR_WSL_RUN=<id>` in `/proc/<pid>/environ`. That file shows the environment at `execve`, so the marker is set by `env` before the probe is exec'd, never by the probe; its children inherit it, since every Linux child ClaudeBar starts gets the app's environment (`LinuxProcesses.environment(for:_:)`). `env` rather than `WSLENV`: the marker stays in the one command line the app builds, and the person's `WSLENV` is untouched. Every mode but `--end` needs it and exits 3 without it.
- **`--end <id>`** sends `SIGKILL` to every process carrying that id, the probe included, and reads again until none is left; `--end all` does the same for any id. It runs without the marker, so it never matches itself. The app runs it when no answer comes 90 s after the deadline, only while that run's `wsl.exe` is still running and the distro still in `wsl.exe -l --running -q`, then kills `wsl.exe`. A probe that ends on its own has ended `wsl.exe` too, and before it exits it ends every other process carrying its id, so nothing the run started (a CLI, something the shell files started) outlives it. Checking and launching aren't one step, so this is best effort: a distro that stops in between is started again, and `--end` finds nothing.

## Where it ships

- Beside `ClaudeBar.exe`: `linux\x64\claudebar-probe` and its resource bundle, in the release zip and the Velopack package, so it's always the app's own version. 27.5 MB more in the zip.
- It runs from there, over drvfs: `/mnt/c/Users/<you>/AppData/Local/ClaudeBarWindows/current/linux/x64/claudebar-probe`, its Linux path from `wsl.exe -d <distro> -e wslpath -u '<Windows path>'`, once per distro per start. Nothing is copied into the distro: running from drvfs is no slower than from ext4.
- **An update.** While a Linux program runs from a folder, Windows can't rename the folder (it can delete it). Velopack applies an update by renaming `current`, and stops only Windows processes first, so an update during a probe fails, changes nothing, and can be tried again. So before *Update* quits the app for Velopack, the app takes every distro's mutex, which waits for a probe the app or the uploader runs. They're released when the app exits, so an hourly upload can still start one before Velopack renames: best effort, and a `--logs-only` run ends inside Velopack's 10 s of retries. If the update can't be set up after they're taken (Velopack's `InstallWhenQuit` throws), they're released at once, before the app says so, so later probes don't wait on an update that isn't coming. A probe that runs across an update keeps its open file, and the version check refuses its answer.
- **An uninstall** deletes the folder, and a deleted file keeps running. So the uninstall hook (`OnBeforeUninstallFastCallback`, which already removes the task and the Run entry) runs `--end all` in each distro in `wsl.exe -l --running -q` first, while the probe is still there.

## Running it

- **When:** for each distro that's on in Settings and running: the full probe at each HUD refresh (every 10 minutes, and *Refresh*), and from phase 2 `--logs-only` at each hourly upload. Only the HUD's refresh runs a tool's CLI in the distro.
- **One at a time,** per distro: the app and the uploader wait on a named mutex for it, as they do for the settings file.
- **How long:** about 25 s warm, most of it Claude's CLI; 57 s on the first run after the distro starts. The HUD shows this PC's logins first and a distro's when its answer comes.
- **It doesn't start a distro on purpose,** best effort: one that stops between the listing and the launch is started again by `wsl.exe`, which takes 27–36 s.
- **It doesn't keep one running.** WSL stops a distro 15 s after its last process ends, and the probe's processes end with it.

## PATH

- **No shell for the CLIs** (`-e`): the fastest launch. Every tool on the PC was found without one, from ClaudeBar's own tool folders. Rejected: `bash -lic` around the probe, which puts the shell files' `PATH` on every CLI and still misses a tool set up in `.zshrc` for a bash user. The login shell runs once per run, for variables only (*The environment*). A variable read with `loginShell: true` (Z.ai's `ZAI_API_KEY`) still comes from ClaudeBar's own login-shell lookup (`$SHELL -l -i -c`).
- **Windows' `PATH` is dropped.** WSL appends it (`appendWindowsPath`), and a Windows npm install's extensionless shim (`…/AppData/Roaming/npm/codex`) would be found before a Linux tool and run Windows' Node. Before anything looks for a CLI, the probe drops every `PATH` entry under one of the distro's Windows-drive mounts, a rule about WSL that belongs in the probe, not the package.
- **The mount rule.** A drive mount is a line of `/proc/self/mountinfo` whose filesystem is `drvfs`, or `9p` with `aname=drvfs` among its options (split on `,`, then `;`); its mount point, unescaped (`\040`), is the root. Under a root means by whole components: `/mnt/cache` isn't under `/mnt/c`, and trailing slashes don't count. `/mnt/wsl`, `/mnt/wslg` and `9p` with `aname=drivers` aren't drives. No `/mnt/` prefix and no `wsl.conf` parsing: `[automount] root` can put drives at `/win/c` or `/c`, and `wsl.conf` can differ from the mounts until a restart. If mountinfo can't be read, the folder of `wslpath -u 'C:\'`, then any one-letter name, is a drive (`/mnt/c/` gives `/mnt/<letter>`; `/c/` gives `/<letter>`, not all of `/`), with a diagnostic.
- **Version managers** aren't found: their folders are added by shell setup, interactively only. ClaudeBar's fix adds `~/.nvm/versions/node/*/bin` (nvm's default first), `~/.volta/bin`, `~/.local/share/fnm/aliases/default/bin`, `~/.local/share/mise/shims` and `~/.asdf/shims` to `commonPaths`, which a child's `PATH` gets too; it helps a ClaudeBar started outside a shell on any Linux.

## The environment

With `-e` there's no shell, so a variable exported only in the person's shell files (`export CODEX_HOME=~/work/codex` in `.bashrc`) isn't in the probe's environment. `DataSources.expandPath` reads the process environment (`DataSources.swift:19-24`), so the probe would read `~/.codex` (`codex.json`: `${CODEX_HOME:-~/.codex}`), an empty folder or a stale login, and the shared-root check would compare the wrong roots. ClaudeBar's fix for version managers finds programs, not this. So the probe reads those variables from the person's login shell, once per run:

- **Which names:** every `${NAME` in the definitions the probe loads (the bundled ones and the person's own in the distro's `~/.claudebar`), valid by `LoginShellEnvironment.isValidName`, collected at startup from the definitions' own encoding, never listed by hand. ClaudeBar parses them in `Paths.expand` (`DataSources/Sources/PathPattern.swift:70-80`), which is internal and reads a `${` only at a path's start. At the pin: `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `KIMI_SHARE_DIR`, `PI_CODING_AGENT_DIR`, `XDG_DATA_HOME`. Not the names of credentials read from the environment (`ZAI_API_KEY`): ClaudeBar reads those through the shell itself when a definition asks (`loginShell: true`), and leaves them out otherwise, on Linux as on the Mac.
- **Never `PATH` or `TZ`,** even when a definition names them: the probe's `PATH` is its own, without the drives (*PATH*), and a shell's has WSL's Windows entries back in it; its `TZ` is the zone the app gave it (*The time zone*), and a shell file that exports another would count the days in that one.
- **How:** `$SHELL` (or `/bin/bash` without one, as ClaudeBar's `LinuxProcesses` chooses) with `-l -i -c '/usr/bin/env -0 > <file> && printf %s @@CLAUDEBAR_ENV_END@@ >> <file>'`, where `<file>` is in a folder only the probe's user can open, made for the run and removed after. `env` is named by its path, so a shell file that rewrites `PATH` can't hide it; the marker is written only when `env` succeeded, so a failed dump is never read as a whole, empty one. Stdin, stdout and stderr are `/dev/null`, in a session of its own, for 3 s at most. A session, with no controlling terminal: `wsl.exe` gives every Linux process one, even started with no console and every handle redirected, and an interactive shell in a background process group of it stops itself (`SIGTTIN`) before reading a file (research). The file is opened by the command's own redirect after the shell files have run, so nothing they print, nor a process they start in the background, can write in it. Only the names above are kept. ClaudeBar's `LoginShellEnvironment` asks for one variable per shell, with its name inside the command, reading stdout, so the probe doesn't reuse it for a list.
- **Use:** each name with a non-empty value is set in the probe's environment before any definition is expanded or any provider made. `expandPath`, the CLIs (whose environment starts from the probe's) and the shared-root check then all see the same roots.
- **Failure:** a timeout, an exit that isn't 0, or a file that isn't only `env`'s entries and the end marker leaves the probe on its plain environment. `environmentImport` says `failed` and why, and Settings says *Couldn't read your shell's settings; custom folders like CODEX_HOME may be missed*. The probe never claims a custom folder it didn't read.
- **Both modes import,** `--json` and `--logs-only`: an upload's days must come from the folders the HUD reads. The shell's start is the cost, once per run: on the PC about 0.1 s warm, and 1.5–3.8 s for the first shell after the distro starts (research); with nvm or conda in `.bashrc` it would be more. The 3 s bound keeps a slow or stuck shell file from holding the run: the first run after a start can meet it and read the plain environment, and the next run imports.
- **Its leftovers:** the shell, and anything its files start, carry the run's marker, so the probe's last step ends them with its CLIs.

## The time zone

A device's day is its own date, in its own zone (ClaudeBar's `docs/features/leaderboard/design.md`, *What does "today" mean across time zones?*), and a distro is part of the PC, so the probe counts in Windows' zone, not the distro's. ClaudeBar on Linux takes its zone from `TZ` (`Internal/Linux/Time/LinuxTimeZone.swift`, read through `DataSources.calendar()`), so the app sets it at launch: each record goes in a day by its own timestamp, in Windows' zone, and `DailyTokens.summed` on Windows labels that day as it labels this PC's. ClaudeBar needs no change. On the PC, a distro in `Asia/Seoul` run with `TZ=America/Los_Angeles` dated records either side of both midnights as Los Angeles does ([research](../../design-concept/wsl/research.md#counting-in-windows-zone-with-tz-2026-11-10)).

- **Which name:** the zone this PC's days are counted in, `DataSources.timeZone()` (`WindowsTimeZone`: the registry key joined to CLDR's IANA zone), as the distro's tzdata names it. ClaudeBar's table is internal to its package, so that call is the only way in: its answer is CLDR's name, which always has a `/`, or a fixed offset, which Foundation names `GMT+0900` (0 is `GMT`).
  - CLDR keeps seven names that tzdata has moved to its `backward` file, which Ubuntu ships apart in `tzdata-legacy`, not installed by default: `Asia/Calcutta`, `Asia/Katmandu`, `Asia/Rangoon`, `Europe/Kiev`, `America/Buenos_Aires`, `America/Godthab`, `America/Indianapolis`. .NET's `TimeZoneInfo.TryConvertWindowsIdToIanaId` gives the same names. The app sends their current names instead (`Asia/Kolkata`, `Asia/Kathmandu`, `Asia/Yangon`, `Europe/Kyiv`, `America/Argentina/Buenos_Aires`, `America/Nuuk`, `America/Indiana/Indianapolis`), as tzdata links them (`L Asia/Kolkata Asia/Calcutta` in `tzdata.zi`).
  - A fixed offset (daylight saving's automatic adjustment turned off, a key the table doesn't know, or one of `WindowsZones.unformattable`): 0 goes as `Etc/UTC`, any other whole number of hours from −12 to +14 (tzdata's `Etc/GMT+12` to `Etc/GMT-14`) as `Etc/GMT-9` for +09:00 (POSIX's sign, reversed), and any other offset has no tzdata name, so none is sent. Never Foundation's own name for an offset (`GMT+0900`): no file has that name, glibc reads it as UTC, and the probe stops on it (SIGILL, exit 132).
- **Every run gets it,** `--json` and `--logs-only`, so the HUD's *today* and an upload's days are the same days. The CLIs inherit it, so a reset time a CLI prints and the one ClaudeBar reads from its screen are in one zone. The environment import never replaces it (*The environment*).
- **The probe checks it first,** before anything reads a zone: `TZ` stands only when `/usr/share/zoneinfo/<TZ>` is a file and Foundation knows the name, which is what `LinuxTimeZone` needs to count in it. Otherwise ClaudeBar counts in another zone and says nothing: on the PC, `TZ=Asia/Calcutta` counted in `GMT` (Foundation knows the name, the file isn't there, so `LinuxTimeZone` takes the OS's offset, fixed), and `TZ=Nowhere/Zone` in the distro's own `Asia/Seoul`. So the probe unsets `TZ`, runs in the distro's own zone as before (the HUD, the CLIs and ClaudeBar in one zone), and answers `days: null`, with `timeZone` the zone it used and a diagnostic: *no time zone data for Asia/Kolkata (/usr/share/zoneinfo/Asia/Kolkata)*. Never a fixed offset or UTC in its place. A distro with no tzdata at all (a slim image, many containers) is refused the same way, for every zone. `TZDIR` doesn't matter: ClaudeBar reads `/usr/share/zoneinfo` and its own zone data.
- **No name** (an offset that isn't a whole number of hours): the app launches without `TZ`, the probe counts in the distro's own zone, and the uploader doesn't send that distro's days.
- **`timeZone` no longer names the distro's own zone,** so Settings' note *its clock isn't Windows'* goes: the days are counted in Windows' zone whatever the distro's clock says. Nothing else needs the distro's own zone. The HUD's reset times cross the wire as instants and Windows shows them in its own zone. What the probe reads in Windows' zone instead of the distro's: mapping scripts and requests ClaudeBar tells the zone, and log times written without one (`LogRecord`, which reads them in the person's zone). Among the built-in definitions the only such time is Claude Desktop's daily counter, a bare date (`claude.json`: `yyyy-MM-dd`), which keeps its label in any zone; Mistral's names `UTC`. A person's own definition with local times would be read in Windows' zone, the same one while WSL keeps the zones equal (`useWindowsTimezone`, on by default).
- **Kept days carry no zone.** ClaudeBar keeps each closed day in the distro under its label (`~/.claudebar/usage-history/<login>.json`, `DayLedger`), and starts that over only when the log's fingerprint changes, which doesn't hold the zone (the scans it keeps between processes are kept per zone). So days a probe without `TZ` closed keep the distro's labels, and a probe with it would answer them as they are: on the PC, runs in other zones answered with the days an earlier run had kept (research). A release of its own ahead of the uploader wouldn't do: a PC that updates straight to phase 2 never runs it. So the probe keeps the zone its kept days were counted in (`~/.local/share/ClaudeBar/wsl-zone`; with none, the distro's own zone, which every probe before this one used), and when the zone it now counts in is another, it removes the ledger's pages (`~/.claudebar/usage-history/*.json`, not the scans) before it reads anything, then writes the new zone. The zone is the one the run counts in, so a run without `TZ`, or with one refused, makes it the distro's own: the pages and the file always agree. A run that can't remove a page reads no days and answers `days: null`. ClaudeBar documents the ledger as a cache that reads the logs again when deleted; the first run after costs one read of the window's logs. Days whose logs a tool has deleted come back as what the logs still hold, which *Late days* never sends smaller for a day before the last upload's; the days from it on are today and yesterday, whose logs no tool deletes. When the zones are equal, as WSL keeps them by default, nothing is removed. A later change of Windows' zone starts them over the same way.

## Folders shared with Windows

Some people point WSL at the Windows folder (`~/.claude -> /mnt/c/Users/<you>/.claude`, `CLAUDE_CONFIG_DIR` or `CODEX_HOME` on `/mnt/c`). Then both sides read the same logs and credentials: the days would count twice and the account show twice. Being on a drive isn't the test: a WSL-only `~/.claude -> /mnt/d/wsl-data/.claude` is never read by Windows, which reads its own `${CLAUDE_CONFIG_DIR:-~/.claude}` (`claude.json`: the folder's default at line 413, the records at 376). The test is whether both read the same place, and a shared source is skipped, not read and then filtered.

- **The app's roots, passed in.** Before each launch, the app writes its own roots per provider to a file of that run's own, `%LOCALAPPDATA%\ClaudeBar\wsl\windows-roots-<id>.json` (the app and the uploader can probe two distros at once), and deletes it when the run ends. The roots are expanded as `TokenLogs` and the factory do (`DataSources.expandPath` with this PC's home and environment): the credential roots, the account folder (`accounts.folder.default`) and the files `dataSources(forDefaultAccount:)` reads; and the log roots, the folder of `usageHistory(forDefaultAccount:)`'s records before the first wildcard. Each is resolved through symlinks and junctions (`GetFinalPathNameByHandleW`). The probe gets the file's Linux path as it gets its own.
- **The probe's side.** It expands the same roots in the distro and resolves each with `realpath`. A root on the distro's own disk maps to `\\wsl.localhost\<distro><path>`, which matches only if the Windows side was pointed into the distro (`CLAUDE_CONFIG_DIR=\\wsl$\...` on Windows). One under a drive mount is mapped to its Windows path from that mount's `path=` option, its `\ooo` escapes undone as the mount point's are (`/mnt/c/Users/<you>/.claude` is `C:\Users\<you>\.claude`), or `wslpath -w` without one. If neither gives a path, or mountinfo can't be read and the fallback mount rule puts the root under a drive, the source fails closed: it's skipped as if shared, the diagnostic says why, and Settings says *couldn't check against Windows* beside it. Counting nothing from a source beats counting it twice.
- **Matching,** pure, in `ClaudeBarShared`, against the same provider's Windows roots. Both sides are normalized first: the `\\?\` prefix `GetFinalPathNameByHandleW` returns is removed (`\\?\UNC\` becomes `\\`), and `\\wsl$\` is read as `\\wsl.localhost\`; then case-insensitive, `\` and `/` the same, no trailing separator. A credential root is shared only when it's the same place as one of Windows' credential roots: an account nested in the folder Windows reads (`…\.claude\wsl` in `…\.claude`) is another login. A log root is compared with Windows' log roots only, and is shared when the two are the same or one is inside the other by whole components (`…\.claude\projects\foo` is under `…\.claude\projects`; `…\.claude-work` isn't under `…\.claude`).
- **What ClaudeBar lets the probe skip,** at `origin/main`, without a change:
  - a whole provider: `isEnabled(forProvider:defaultValue:)`, read by `Provider.productSwitch` (`Provider.swift:103`);
  - the data source in use: `dataSourceKind(forProvider:)` (`Configuration.activeKind`), and a fallback only when the definition makes it switchable (`Configuration.isFallbackEnabled`, `enabledBySetting`). Claude's `cli` falls back to `api` always; `api` to `cli` only while `cliFallbackEnabled` is on. Codex's `rpc` falls back to `tty` always.
  - Nothing turns off one source or points it elsewhere: the paths come from the definitions and `${CLAUDE_CONFIG_DIR}`, `${CODEX_HOME}` in the environment. The smallest hook would be a per-kind switch that `Configuration` consults when it picks the active source and follows a fallback.
- **So the probe skips per provider, per kind of source,** with no change in ClaudeBar:
  - a shared credential root turns the provider off for the refresh, through the probe's settings (a view over `ClaudeBarSettings` answering `isEnabled` false), so the probe never reads or refreshes a Windows `.credentials.json`;
  - a shared log root leaves that provider out of the probe's `ProviderTokenLogs`, this repo's code;
  - each skip is in `skipped`, and Settings says *shared with Windows* beside it.
  - Tradeoff: a provider with one shared credential source and one distinct loses its WSL limits; its distinct logs still count. Per-source skipping keeps those limits but needs the hook above, for a case the built-in definitions don't make: Claude's and Codex's sources all read their account folder.

## The HUD, Limits and Settings

- **A WSL login is a login of its own,** beside the Windows one: `Claude · WSL`, or `Claude · WSL Ubuntu-26.04` when more than one distro is read. Its lineup id is the probe's prefixed with the distro (`wsl:Ubuntu-26.04/claude`); a group keeps both (`wsl:Ubuntu-26.04/omp/Claude · work`).
- **WSL is said once per name, after the login's or the group's own:** a group's HUD row is `Claude · work · WSL`, and where Limits, Settings → HUD and Narrator add what it was read through, that name doesn't say it again: `Claude · work · WSL · via Oh My Pi`, not `… · via Oh My Pi · WSL`. Each look from a distro's answer sends its place (`WSL`, `WSL Ubuntu-26.04`) beside its name, so the app knows what to leave out; the distro's own look, for a failed run with nothing kept (`WSL Ubuntu-26.04`), names no login and has none.
- **The Swift side merges them,** so `cbw_hud_reading` keeps its shape: each distro's tools, problems and looks after this PC's. The C# app learns one new problem kind, `notRunning`: the distro isn't running, and its last numbers stay dimmed with their time (*WSL isn't running · numbers from 14:05*).
- **A stopped distro has the rows it has while it runs,** each saying it isn't running: a tool or group with numbers is its own row, dimmed, with their time; omp's accounts it measures nothing for (a note alone) are one row, `Oh My Pi · WSL`, *WSL isn't running*, not one row each beside a *no limits to show*. The strip's dots are the same rows. Limits keeps a card for each account, as while it runs, each saying *WSL isn't running*.
- **Not shown for WSL:** `notSetUp`, which would list every provider twice, and a failure that says Linux can't read that source at all (Antigravity's local server).
- **Settings → Tools in WSL:** the distros `wsl.exe -l -q` lists, without `docker-desktop*` and `rancher-desktop*`; for each, whether it's running, an on/off switch (on by default once a reading finds a tool), and from its last reading the tools and where, with *shared with Windows* beside a skipped source, a note when its days couldn't be counted in Windows' zone (*The time zone*), and one when its shell's settings couldn't be read (*The environment*). Kept in `app.json` (`wsl: {"Ubuntu-26.04": {"on": true}}`) with each distro's last reading.

## The Leaderboard (phase 2)

- **The uploader runs `--logs-only`** in each running distro that's on, and this app's `TokenLogs.days(in:)` returns each distro's days beside this PC's logins, as plain `LoginDays`: one per provider in its `days`, each day a `DailyUsageStat` dated at the start of its label in this PC's calendar, with the five token counts (`totalTokens` is input, output and unsplit, so `DailyTokens(provider:stat:)` gives back the same day; nothing else about a day leaves the device). `providersWithLogs` adds the distros' providers. ClaudeBar's `DailyTokens.summed` labels each as the probe did and adds it to this PC's day, behind the `sharing` filter. A request counts once: a shared log is read on the Windows side only. One device, one key, the server's cap, unchanged.
- **The days are Windows' days** (*The time zone*): the probe put each record in a day by its own time, in Windows' zone, so a distro's day and this PC's with the same label are the same day. A distro whose days were refused (`days: null`), or whose zone has no name, adds no new days; its kept days stay.
- **No day shrinks because a distro couldn't be read.** An upload sends every day from `lastUpload`'s day on as read, larger or smaller, so each distro's last `days` are kept with their labels and the zone they were counted in (`%LOCALAPPDATA%\ClaudeBar\wsl\days\<distro>.json`; the roots files are in `wsl\`) and sent while it isn't running. Every run whose days were counted in the zone the app sent keeps them, the HUD's runs too, while it still holds the distro's mutex, so a slower run can't put older days over newer ones. Only an answer with days replaces them; one refused for its zone doesn't. The app's own uploads (*Join*, *Upload now*, a device added) and its preview read the kept days, at most one HUD cadence old while the distro runs; only the hourly uploader runs `--logs-only` first, so an upload the person waits for never waits on a distro's mutex. An answer is what the logs say now, as for this PC: a tool that deletes its logs (Claude Code's `cleanupPeriodDays`) can make a re-sent day smaller on either side, and keeping the larger total would count tokens no log holds (CONTRIBUTING rule 5).
- **A late day still goes (*Late days*).** ClaudeBar's uploader sends only the days from the day of `lastUpload` on, and the refused ones (`LeaderboardUploader.swift:104-116`), because *the server already took* the days before (its comment at 110-111): the cut is where an upload resumes, not a rule that an uploaded day is final, and an upload *replaces, never adds* (`LeaderboardUploader.swift:9-10`, `docs/features/leaderboard/design.md:461`). WSL makes the days it misses common:
  1. A distro turned on, or read for the first time, after this PC has uploaded: Windows uploaded on Nov 4, WSL is on from Nov 5 with logs from Nov 1-3. Those days are before the cut.
  2. A distro stopped at upload times. WSL stops an idle distro after 15 s (*It doesn't keep a distro running*), so one used now and then is often stopped on the hour: it runs again on Nov 6 with Nov 2-5 logs the kept days didn't have. Kept days stop a day shrinking; they can't add days that arrive late.

  The Mac loses days the same way today: turning sharing on for a provider after the first upload (`share(_:)`, `LeaderboardMembership.swift:389-393`, leaves `lastUpload` where it is), adding a login with past logs, and Mistral's sessions, whose tokens are dated by the session's start (`at.fromPath` in `mistral.json`) and grow after midnight, until the day closes (`DayLedger.closesAfter`, an hour after midnight). Claude, Codex and omp date each record by its own `timestamp`, so a session that spans midnight lands on both days and isn't lost.

  The change: the membership keeps, per provider and day in the 30-day window, the total this device last sent and the server took (not a refused one). An upload sends the days from `lastUpload`'s day on, as today, and also any earlier day in the window whose total is now larger than the one kept; a day with none kept counts from 0. Days that leave the window leave the record. Unchanged days aren't sent again, so the hourly traffic stays as it is, and the hour that would send exactly what the last one did is still skipped. Refused days keep their own retry. An earlier day goes only when it grew, never smaller: today such a day is never sent again, so the server keeps what it took, and *no rule lowers a number on a guess* (`design.md:354`). Merged as tddworks/ClaudeBar#703: a record from before the change has no `sent`, and from its first start the membership holds the days before that record's `lastUpload`'s day (`heldBefore`, `LeaderboardMembership.swift:662-671`): they go only when refused, until they leave the window, so an update re-sends nothing. Only days sent and taken are recorded (`recordUpload`, 448-461), so no day is ever kept as sent without going, and the distros' days join this app's `TokenLogs` from the start, counting from 0. What the hold costs WSL: a distro's day dated before `heldBefore`, the day of this PC's last upload before v0.1.17, never reaches the board. (`sent` and `heldBefore` are internal to the package, so the client couldn't gate on them anyway.) Reading thirty days each hour is cheap: closed days come from the `DayLedger` (`UsageHistory.swift:66-91`), open ones from the scans #659 keeps between processes (the Windows uploader's read went from 117 s to 3 s).

  On Windows, `SettingsFile.merge(_:since:onto:)` (`SettingsFile.swift:96-105`) saves the record field by field, so the new field is added there, and to its stored form, with the pin bump.
- **A distro switched off or removed** (`wsl --unregister`) is like a provider whose sharing is turned off: `stopSharing` only stops uploads, and *days already uploaded stay until you leave* (ClaudeBar's Leaderboard README). Its kept days are frozen, not deleted, and still sent, so the days the server took with them don't shrink, until they leave the upload window or the person leaves the Leaderboard, which deletes them.

## Keeping the probe and the app in step

- `ProbeReading` is one type, encoded by the probe and decoded by the app from the same source file; `HudReading`, `HudMonitor.Answer` and the problem and look types become `Codable`. Its days are ClaudeBar's `DailyTokens`, so the label format is ClaudeBar's on both sides.
- The probe says its version; another version's answer is a failure, never read in part.

## Errors

| What happens | What the person sees |
|---|---|
| No WSL, or no distro | Settings says *WSL isn't installed* or *No distros* |
| The distro is stopped | `notRunning`, the last numbers dimmed |
| `wsl.exe` fails, or the probe can't start (no `libcurl.so.4`, not x64, the drive not mounted, no marker: exit 3) | `failed`: *ClaudeBar couldn't run in Ubuntu-26.04: <the error's first line>*, on the HUD, Limits and Settings |
| The answer comes at the deadline | Logins still reading say `failed`, *Took too long in WSL* |
| No answer 90 s after the deadline | `--end`, then `wsl.exe` killed; `failed`, and kept days stay |
| Another version answered, or the JSON doesn't parse | `failed`, *ClaudeBar's WSL reader is from another version* |
| A source is shared with Windows | Not an error: it's skipped, and Settings says *shared with Windows*. A root under a drive mount that can't be mapped to a Windows path is skipped too, and Settings says *couldn't check against Windows*, with a diagnostic |
| The login shell can't be read (a timeout, an exit that isn't 0, a file cut short or with something else in it) | Not an error: the probe runs on its plain environment, and Settings says *Couldn't read your shell's settings; custom folders like CODEX_HOME may be missed* |
| The upload can't read a distro (phase 2) | Its kept days are sent; the log says why |
| The distro has no time zone data for Windows' zone, or none at all | Not an error for the HUD, which reads in the distro's own zone; its days aren't sent (its kept days are), Settings says *No time zone data for Asia/Kolkata in Ubuntu-26.04, so its days aren't on the Leaderboard; installing tzdata in it fixes this*, and the probe's diagnostic names the file |
| Windows' zone has no tzdata name (a fixed offset that isn't a whole number of hours) | Its days aren't sent; Settings says *Windows' time zone has no name Linux knows, so WSL days aren't on the Leaderboard* |
| An update starts during a probe | Velopack's *Unable to start the update, because one or more running processes prevented it*; the old version stays, and *Update* can be tried again |
