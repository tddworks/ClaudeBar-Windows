# Updates (design, 2026-11-02)

On the Mac, ClaudeBar updates itself with Sparkle: it notices a new release, says so, and one button installs it and restarts. Until now the Windows app was a zip you extracted again by hand. This makes it the same: an installer for the first time, then an *Update* button.

## Decisions

- **Velopack** ([velopack.io](https://velopack.io), 1.2.161, the library and `vpk` at the same version). `vpk pack` turns the published folder into an installer (`Setup.exe`), a full package and a delta package; the app's `UpdateManager` reads them from this repo's GitHub releases (`GithubSource`) and applies them with Velopack's `Update.exe`. Rejected: a minimal updater of our own (the releases API, the zip, its `.sha256`, a helper exe that swaps the folder). Velopack does that with deltas, a lock against two updates at once, a SHA-256 check of every package, hooks, an Apps entry and an uninstaller, and nothing below blocks it. Rejected: MSIX, which needs a signed package to install at all.
- **It fits the app as it is:**
  - *Unpackaged, self-contained WinUI 3.* Velopack packs a folder and runs its main exe; it doesn't care what's inside. The app carries the Windows App SDK runtime (`WindowsAppSDKSelfContained`), so there is no bootstrapper and no prerequisite for `Setup.exe` to install.
  - *`ClaudeBarNative.dll`, `claudebar-upload.exe`, the Swift runtime and the resource bundles* sit beside `ClaudeBar.exe` and travel in the same package. `Update.exe` stops every process running from the install folder before it swaps it, the hourly uploader too if an upload is running then; that upload runs again the next hour.
  - `Program.Main` calls `VelopackApp.Build().Run()` before anything else, as Velopack requires: on an install, update or uninstall it runs the hook and exits, before the single-instance check.
- **The install folder is `%LOCALAPPDATA%\ClaudeBarWindows`, not `%LOCALAPPDATA%\ClaudeBar`.** Velopack installs to `%LOCALAPPDATA%\<package id>` and replaces or deletes that whole folder on install and uninstall. `%LOCALAPPDATA%\ClaudeBar` holds `settings.json`, `app.json` and the logs, so the package id is `ClaudeBarWindows` and Velopack never touches them. The app runs from `…\ClaudeBarWindows\current\ClaudeBar.exe`; an update replaces `current`, so that path stays the same from one version to the next.
- **The hourly upload follows the exe.** The task runs `claudebar-upload.exe` beside `ClaudeBar.exe`. Three places keep it pointing there, each changing it only when it points elsewhere (it reads the task's command from `schtasks /Query /XML`): the install and update hooks (`OnAfterInstallFastCallback`, `OnAfterUpdateFastCallback`, which may take 15 seconds and show no UI), and the app at each start, as before. So a zip install moved to Setup, or a future change of folder, takes the task over without waiting for the app to open. The hooks never create the task: only joining does.
- **Uninstalling removes the task and the Run entry** (`OnBeforeUninstallFastCallback`), the Run entry only when it starts this copy. It keeps the membership: `%LOCALAPPDATA%\ClaudeBar` and the key in Credential Manager stay, as Velopack leaves anything outside its folder. Leaving the Leaderboard, in Settings, is still what deletes your data on the server; the README says to do that first.
- **Pre-releases are read.** Every release so far is a GitHub pre-release, so `GithubSource` is made with `prerelease: true`, which reads stable releases too. The channel is Velopack's default for the platform, `win`, written into the package by `vpk pack --channel win`; the app doesn't choose one.
- **A local feed, for trying an update before a release.** With `CLAUDEBAR_UPDATE_FEED` set to a folder, the app reads packages from it (`SimpleFileSource`) instead of GitHub, so a build can be packed twice (`vpk pack --packVersion 0.1.8-local.1`, then `.2`) and updated on a PC without publishing anything ([CONTRIBUTING](../../CONTRIBUTING.md#trying-an-update)). Nothing else changes: the same hooks, the same button.
- **The zip stays for a release or two,** for whoever installed by hand. Its folder has no `sq.version`, so Velopack doesn't count it as installed, and Settings says updates come with the installed app.

## What the person sees

- **A check at start and every 4 hours,** two minutes after the window starts, so it doesn't compete with the first reading. Never while Windows says the person is busy: a full-screen app or game, Direct3D full screen or presentation mode (`SHQueryUserNotificationState`); then it tries again in 15 minutes. The check reads the release list only; nothing is downloaded until the person asks.
- **When one is found:** an InfoBar above the page, *ClaudeBar 0.1.9 is available*, with *Update*; and one Windows notification per version, with *Update*. The last version notified is kept in `app.json` (`updateNotified`), so a restart doesn't notify again; a newer version does.
- **Settings → Updates** shows the installed version and what the last check found, with *Check for updates*; when a version is available, *Update* too. *Update* downloads it (a delta when Velopack has one, with its progress), then quits ClaudeBar, which `Update.exe` waits for, installs it and starts the new version. That version opens its window and says *Updated to 0.1.9*. `ClaudeBar.exe --update` asks the running window to do the same, as the notification's button does.
- **What can go wrong is said, in place:** the check or the download failing (offline, GitHub's rate limit of 60 reads an hour from one address, a package failing its SHA-256) shows under the version, and *Check for updates* tries again. A copy that isn't installed (the zip, or `build.ps1`'s output) says *Updates come with the installed app: install it with Setup.exe from Releases*.
- **SmartScreen.** The preview isn't code-signed. `Setup.exe`, downloaded with a browser, carries the mark of the web, so SmartScreen may stop it once (*More info*, *Run anyway*). Updates are downloaded by the app, not a browser, and carry no mark, so they never ask.

## Releases

The tag workflow builds and tests as before, then, still in the build job (no write token):

1. `vpk download github --pre --channel win` fetches the latest Velopack release's full package, which `vpk pack` needs to make a delta. The first Velopack release (0.1.8) has none, so it ships a full package only.
2. `vpk pack --packId ClaudeBarWindows --channel win --mainExe ClaudeBar.exe --packTitle ClaudeBar --shortcuts StartMenuRoot --noPortable` makes `ClaudeBarWindows-win-Setup.exe`, `ClaudeBarWindows-<version>-full.nupkg`, `ClaudeBarWindows-<version>-delta.nupkg` from 0.1.9 on, and `assets.win.json`. No Portable zip: the plain zip already covers that.

The release job, the only one that can write, uploads them with `vpk upload github --channel win` into a draft release, which adds `releases.win.json` (what `UpdateManager` reads) and the legacy `RELEASES`. It adds the plain zip, then a `.sha256` beside every file in the release, and only then publishes it as a pre-release: the app never sees a release that's half uploaded, because GitHub doesn't list drafts to it.
