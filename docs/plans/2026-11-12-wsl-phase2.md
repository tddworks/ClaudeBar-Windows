# Tools in WSL, phase 2: Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Build phase 2 of [the WSL design](2026-11-03-wsl-design.md): a WSL distro's days on the Leaderboard, counted in Windows' zone, added to this PC's days, never making a day smaller when the distro can't be read, and the person told once.

**Architecture:** The app launches the probe with Windows' zone in `TZ` (`WslZone`, shared). The probe checks the zone before anything reads one, starts the distro's kept days over when they were counted in another zone, and answers `days: null` when it can't count in Windows' zone. On Windows, every run whose days were counted in the zone it was sent keeps them under the distro's mutex (`WslKeptDays`). The Leaderboard's `TokenLogs` becomes `DeviceTokenLogs`: this PC's logins, plus each distro's kept days as plain `LoginDays`; the hourly uploader first runs `--logs-only` in each running distro that's on, so its kept days are fresh. ClaudeBar's uploader does the rest, unchanged. The app says once that WSL days now count.

**Tech Stack:** Swift 6.3.3 (ClaudeBarKit at v0.5.29, `aa88b0f4`), Glibc on Linux, WinSDK on Windows; C# / WinUI 3; Swift Testing; MSTest; GitHub Actions (`windows-latest`, and `ubuntu-latest` in `swift:6.3.3-noble` with `--init`); Windows PowerShell 5.1 for the PC checks.

## What the code at `main` says, checked for this plan

ClaudeBar at v0.5.29 (`aa88b0f4`, #723, checked on 2026-11-22: #723 moved only the app's own modules, so every package path below is where it was, and `Modules/Leaderboard/Sources` is unchanged since `beee51de`; the next commit, `e999eb90`, changes only `CHANGELOG.md`), this repo at `ac4c247` (#50).

1. **How an upload reads.** `LeaderboardUploader.upload` reads `logs.days(in: DateRange.last(30, endingOn: now, calendar: calendar))` once (`LeaderboardUploader.swift:82-90`) and sends `Due` of `membership.dailyTokens(from:)` (`DailyTokens.summed` over `sharing`). `Due` (122-145): every day from `lastUpload`'s day on goes **as read**, larger or smaller; an earlier day goes only when its total is larger than `sent` holds for it, or has none in `sent`; a day before `heldBefore` only when refused. So a distro that stops reading must not make today's day smaller (*No day shrinks* in the design): its kept days stand in for it. An earlier day can't shrink anyway.
2. **What `TokenLogs.days(in:)` must return for a distro.** `TokenLogs` (`DailyTokens.swift:82-88`) is `providersWithLogs` and `days(in:)`, nothing more. `LoginDays(providerId:days:)` with `DailyUsageStat`s; `DailyTokens(provider:stat:calendar:)` (`DailyTokens.swift:31-36`) labels a stat by `stat.date` in the calendar, takes `inputTokens`, `outputTokens`, `cacheCreationTokens`, `cacheReadTokens`, and `unsplit = totalTokens - input - output`. So a kept `DailyTokens` goes back as a stat dated at its label's start in this PC's calendar, `totalTokens = input + output + unsplit`, and `summed` adds it to this PC's day of the same label (`DailyTokens.swift:51-62`). `DailyUsageStat.init(date:totalCost:totalTokens:workingTime:sessionCount:inputTokens:outputTokens:cacheCreationTokens:cacheReadTokens:…)` takes the rest with defaults (`DailyUsageStat.swift:54-68`). `Due` drops a day before the window's first (`day.day >= firstDay`), so kept days outside the 30 needn't be filtered for correctness; `DeviceTokenLogs` filters them anyway, as `LoginDays.within` does for this PC's.
3. **`sent` and a record from before it.** A record without `sent` (v0.1.16's) gets `heldBefore` = its `lastUpload`'s day (`LeaderboardMembership.swift:662-671`); `recordUpload` records only the days sent and taken (448-461). Nothing is ever recorded as sent without going, so the design's gate (*the distros' days join `TokenLogs` only once that record exists*) isn't needed, and the client couldn't apply it: `sent` and `heldBefore` are internal to the package (36-40). What the hold does mean: a distro's day before `heldBefore`, the day of this PC's last upload under v0.1.16, never reaches the board (accepted, *Decisions*, 1).
4. **The zone's name on Windows.** ClaudeBar's `WindowsZones` table (`iana`, `Modules/DataSources/Sources/Internal/Time/WindowsZones+Table.swift`) and its `unformattable` set (`WindowsZones.swift:27-29`) are internal. A client gets `DataSources.timeZone()` (`Ports/TimeZoneSource.swift:17`): `WindowsZones.zone(key:daylightSavingOff:secondsFromGMT:)`'s answer (`WindowsZones.swift:14`), a CLDR name, or `TimeZone(secondsFromGMT:)` when daylight saving's adjustment is off, the key is unknown, or the name is one Foundation on Windows can't format in (`America/Mazatlan`, `America/Whitehorse`, `Asia/Qyzylorda`, `Etc/UTC`, `Europe/Volgograd`). Every name in the table has a `/` (all 139, checked again at v0.5.29); Foundation names a fixed offset `GMT+0900`, `GMT-0500`, `GMT+0530`, and 0 `GMT` (checked on macOS Foundation; the research saw `GMT+0900` on Linux). So `WslZone` tells them apart by the `/`, and for a fixed offset uses `secondsFromGMT(for:)`. Foundation on Windows has no public Windows-to-IANA call; .NET's `TimeZoneInfo.TryConvertWindowsIdToIanaId` has one (the research: the same seven old names), but the launch is built in Swift, so .NET isn't used.
5. **The seven names.** Of the table's 139 names, eight are links in tzdata's `backward` file (eggert/tz `main`, fetched 2026-11-12): the design's seven and `Atlantic/Reykjavik` (→ `Africa/Abidjan`). On the PC (`tzdata 2026e-0ubuntu0.26.04.1`, no `tzdata-legacy`) exactly the seven had no file (research): Debian and Ubuntu keep in `tzdata` the `backward` names that are still `zone.tab` locations, and `Atlantic/Reykjavik` is one. So the seven stand; `WslZone` renames them, and the probe's own check (Task 3) refuses any name a distro still lacks, with a diagnostic.
6. **`Etc/GMT` names.** tzdata has `Etc/GMT-14` through `Etc/GMT+12`: a fixed offset of −12 h to +14 h in whole hours gets a name, 0 is `Etc/UTC`, anything else none.
7. **The kept days in the distro.** `DayLedger` keeps closed days under their label in `~/.claudebar/usage-history/<login>.json` (`FileLedgerStore`, `Modules/Providers/Sources/DayLedger.swift:70-93`; a page is `LedgerPage`, public, 52-61), its page's `fingerprint` from `UsageLog` (`Modules/DataSources/Sources/UsageLog.swift:478-501`), which holds no zone; the scans are named with the zone (503). `UsageHistory.days(in:)` keeps each closed day it read (`Modules/Providers/Sources/UsageHistory.swift:89-96`, through `DayLedger.keep`, which writes only when it has a day), so whether a page's file was written says nothing of whether it was removed first. The design's test *a third run in that zone removes nothing (the pages' times unchanged)* can't tell; Task 5 checks it with a day planted in a page instead.
8. **`Optional` on the wire.** Swift's synthesized `Encodable` leaves a `nil` optional out (`encodeIfPresent`), and the synthesized `Decodable` reads a missing key as `nil`. So `days: null` crosses as no `days` key; both sides read either.
9. **The app uploads too.** `cbw_join`, `cbw_join_device` and `cbw_upload_now` run `client.uploader(for:).uploadNow()` (`Exports.swift:162,211,267`), and `cbw_preview` reads `client.logs` (131); `cbw_state` lists `client.logs.providers` (83-85). An upload from the app without the distros' days would send today's day smaller (point 1). So the distros' days go in `Client.logs` for every process; the design only named the hourly uploader.
10. **`@testable import` of ClaudeBar's modules** works from a test target of a package that depends on it, by path or by URL (checked on a Mac, SwiftPM 6.4.2, `swift test`): the probe's tests can read `WindowsZones.iana` to check every name the app can send (Task 3). The product is still `ClaudeBarKit`, with `DataSources` among its targets (`Package.swift:50`).
11. **A kept day doesn't read smaller (new in v0.5.29).** `UsageHistory.settled` (`UsageHistory.swift:102-112`) keeps a closed day the ledger holds when a re-read says less, so a distro's answer for a closed day doesn't shrink when a tool deletes its logs; an open day (today, and yesterday until an hour after midnight) is what the logs say. Windows keeps each answer as it is (design, *No day shrinks*), and for two distros on one folder takes the latest reading, not the largest (correction 10).

## Design corrections in this PR

`docs/plans/2026-11-03-wsl-design.md` is changed in the same PR as this plan:

1. *A late day still goes*: the paragraph on a device from before the change, and the test *a distro's days are left out while the Late days record doesn't exist*, now say what #703 does: `heldBefore` holds the days before the old record's last upload; nothing is recorded as sent without going, so the distros' days join from the start; a distro's day before `heldBefore` never goes (point 3). Its citations of the uploader before #703 now say they're at `bcead725`.
2. *No day shrinks*: kept days live in `%LOCALAPPDATA%\ClaudeBar\wsl\days\<distro>.json` (the roots files are in `wsl\`), with the zone they were counted in; every run whose days were counted in the zone it was sent writes them, under the distro's mutex, the HUD's runs too; the app's own uploads and its preview read them, and only the hourly uploader runs `--logs-only` first (point 9).
3. *Which name*: through `DataSources.timeZone()`, a named zone told from a fixed offset by its `/`, whole hours from −12 to +14 only (points 4, 6).
4. *Kept days carry no zone*: `wsl-zone` says the zone of the last run that read days, so a run without `TZ`, or with one refused, makes it the distro's own; a run that can't remove the pages reads no days and answers `days: null`.
5. *Tests*: the zone runner test computes each record's expected day with a calendar in that zone (moving the records by whole days crosses Los Angeles' daylight saving changes, and `2026-11-09T07:30Z` is then on the 9th); *removes nothing* is checked with a planted day (point 7); *every key gives a name* runs in `linux/` through `@testable import DataSources`.
6. *The probe's answer*: `days: null` may cross as a missing key (point 8).

Found by review of this PR (CodeRabbit), and changed in the design too:

7. *No day shrinks*: a run whose shell settings couldn't be read doesn't replace the kept days. It may have read `~/.codex` for a `CODEX_HOME` set in `.bashrc`, and the first run after a distro starts can take 1.5-3.8 s in the login shell against a 3 s limit (phase 1 plan, *The environment import's cost*), so this is a common case, not a corner. And a provider whose log root a run couldn't check (`uncheckable`) keeps its kept days from the run before, in the same zone (new: *A root a run couldn't check keeps the days from before*).
8. *Kept days count only while they still mean what they did* (new): kept days from another zone than the one the app sends now are left out, and so are a provider's kept days whose log root this PC now reads. For the second, the probe answers `logRoots`, the log roots its days came from in Windows form, and Windows keeps them with the days.
9. *A distro switched off or removed*: the merged design deleted the kept days on leaving the Leaderboard. That can't hold. The HUD's runs write the kept days whether the person is on the board or not, since the preview needs them before *Join*. A run that holds a distro's mutex when the person leaves writes them back after the delete. So leaving deletes nothing on this PC, as ClaudeBar's ledger isn't deleted either (kept, *Decisions*, 5).
10. *A log root two distros read counts once* (new): two distros reading the same folder on a Windows drive that Windows doesn't read would both count it. Kept entries whose `logRoots` overlap for a provider make a group, and the group counts one reading of that provider: the one read last (`readAt`, per provider), the first by distro name on a tie. The second review of it showed why not the largest reading: a reading taken after a tool deleted lines would never replace an older, larger one, and today would keep counting tokens no log holds; the latest is what one reader of that folder would send. A distro stopping, switched off or removed keeps its file, so the latest reading stays until another distro answers: no day drops and none counts twice. The rule reads only the kept files, so the app and the uploader agree.
11. *Errors* (new rows) and Settings: a run that couldn't start the kept days over answers `days: null` too, and Settings says that, with the probe's detail, rather than the tzdata note, which wouldn't fix it. The tzdata note is only for `no time zone data`; a zone whose file is there but which the probe's Foundation doesn't know (`no time zone named`), or a `TZ` that isn't a plain name, gets its own note, since tzdata wouldn't fix those either.

```swift
/// Each distro's last days, kept for the Leaderboard while it can't be read.
public struct WslKeptDays: Sendable {
    public struct Entry: Codable, Equatable, Sendable {
        public let distro: String
        /// The zone the days were counted in: the one the app sent.
        public let timeZone: String
        /// When the run that wrote this answered.
        public let answeredAt: Date
        /// When each provider's days and roots were read: `answeredAt`, or the
        /// earlier entry's time for a provider carried over (`entry(...)`).
        public let readAt: [String: Date]
        public let logRoots: [ProbeReading.LogRoot]
        public let days: [DailyTokens]
        public init(distro: String, timeZone: String, answeredAt: Date, readAt: [String: Date],
                    logRoots: [ProbeReading.LogRoot], days: [DailyTokens])
    }
    /// A log root of a distro's that another's kept entry reads too.
    public struct SharedLog: Codable, Equatable, Sendable {
        public let provider: String
        public let windowsPath: String
        /// The other distros of its group, by name (Swift's `<`).
        public let with: [String]
        public init(provider: String, windowsPath: String, with: [String])
    }
    /// What `current` leaves: the entries as they count, each line for the
    /// log, and each distro's shared log roots.
    public struct Counted: Equatable, Sendable {
        public let entries: [Entry]
        public let leftOut: [String]
        public let shared: [String: [SharedLog]]
    }
    public static var folder: URL { get }       // WslProbe.folder/days
    public init(folder: URL = WslKeptDays.folder)
    public func save(_ entry: Entry) throws      // temp file, then moved over `<distro>.json`
    public func all() -> [Entry]                 // every file that decodes, by distro name
    public func entry(for distro: String) -> Entry?
    public static func entry(distro: String, reading: ProbeReading, days: [DailyTokens], answeredAt: Date, earlier: Entry?) -> Entry
    public static func current(_ entries: [Entry], zone: String?, windows: [ProviderRoots]) -> Counted
    public static func logins(_ entries: [Entry], in range: DateRange, calendar: Calendar) -> [LoginDays]
}
```

`current`'s lines, exactly (`<zone>` is `none` when nil):

- `WSL <distro>: kept days left out: counted in <their zone>, and Windows' zone is <zone> now`
- `WSL <distro>: kept <provider> days left out: Windows reads <windows root> now, and they came from <root>`
- `WSL <distro>: kept <provider> days left out: <root> is read by <winner> too, and its reading is the latest`

### The HUD reply's `wsl` (Slice C writes it, Slice D reads it)

Phase 1's `{installed, distros: [{name, running, on, probing, answeredAt, reading, error}]}`, with:

- `timeZone`: `WslZone.name` of Windows' zone, the name the app sends (`"Asia/Seoul"`), or `null` when it has none. Always present.
- `leaderboard`: what the Leaderboard counts from WSL now: from `WslKeptDays.current(kept.all(), zone:, windows:)`'s entries, each distro with the providers that have a day with tokens in the last 30 days, providers sorted, distros sorted, a distro with none left out; `[]` when none.
- each distro's `sharedLogs`: `Counted.shared[name]` as `[{"provider", "windowsPath", "with"}]`, `[]` when none. It comes from the kept files, so a distro without a reading has it too.
- each distro's `reading.days` may be absent or `null`.

```swift
import Foundation

/// The name Windows' zone goes to a distro by, in `TZ`
/// (docs/plans/2026-11-03-wsl-design.md, The time zone). `DataSources.timeZone()`
/// is CLDR's name for Windows' key, which always has a `/`, or a fixed offset,
/// which Foundation names `GMT+0900` or `GMT`: no file has that name, glibc
/// reads it as UTC, and the probe stops on it.
public enum WslZone {
    /// CLDR's names that tzdata moved to its `backward` file, which Ubuntu
    /// ships apart in `tzdata-legacy`, by the names tzdata links them to.
    public static let renamed: [String: String] = [
        "America/Buenos_Aires": "America/Argentina/Buenos_Aires",
        "America/Godthab": "America/Nuuk",
        "America/Indianapolis": "America/Indiana/Indianapolis",
        "Asia/Calcutta": "Asia/Kolkata",
        "Asia/Katmandu": "Asia/Kathmandu",
        "Asia/Rangoon": "Asia/Yangon",
        "Europe/Kiev": "Europe/Kyiv",
    ]

    /// The name a distro's tzdata knows `zone` by at `date`: a named zone by
    /// its current name; a fixed offset of whole hours as `Etc/GMT∓h` (POSIX's
    /// sign: +09:00 is `Etc/GMT-9`), tzdata's −12 to +14; none as `Etc/UTC`.
    /// nil for any other offset: no tzdata name counts as it does.
    public static func name(for zone: TimeZone, at date: Date) -> String? {
        if zone.identifier.contains("/") { return renamed[zone.identifier] ?? zone.identifier }
        let seconds = zone.secondsFromGMT(for: date)
        guard seconds % 3600 == 0 else { return nil }
        let hours = seconds / 3600
        if hours == 0 { return "Etc/UTC" }
        guard (-12...14).contains(hours) else { return nil }
        return hours > 0 ? "Etc/GMT-\(hours)" : "Etc/GMT+\(-hours)"
    }
}
```

```swift
import Foundation

/// Whether the probe can count in the zone the app sent (design, *The time
/// zone*). ClaudeBar's `LinuxTimeZone` takes `TZ` only when its file is under
/// `/usr/share/zoneinfo`, else the OS's offset, fixed; Foundation falls back to
/// `/etc/localtime` for a name it doesn't know; and a name like `GMT+0900`
/// stops the process. None of that says so, so the probe checks first.
public enum ZoneCheck {
    public enum Verdict: Equatable, Sendable {
        /// No TZ: the distro's own zone, as every probe before phase 2.
        case none
        case accepted(String)
        /// Why, for the diagnostics.
        case refused(String)
    }

    public static func check(_ tz: String?, zoneinfo: String = "/usr/share/zoneinfo") -> Verdict {
        guard let tz, !tz.isEmpty else { return .none }
        let parts = tz.split(separator: "/", omittingEmptySubsequences: false)
        guard !tz.hasPrefix(":"), parts.allSatisfy({ !$0.isEmpty && $0 != "." && $0 != ".." }) else {
            return .refused("TZ \(tz) isn't a zone name")
        }
        let file = zoneinfo + "/" + tz
        var info = stat()
        guard stat(file, &info) == 0, (info.st_mode & S_IFMT) == S_IFREG else {
            return .refused("no time zone data for \(tz) (\(file))")
        }
        guard TimeZone(identifier: tz)?.identifier == tz else { return .refused("no time zone named \(tz)") }
        return .accepted(tz)
    }

    /// Checks `TZ` and, when refused, unsets it before anything reads a zone
    /// (Foundation keeps the first zone it reads), so the HUD, the CLIs and
    /// ClaudeBar all count in the distro's own.
    public static func apply() -> Verdict {
        let verdict = check(ProcessInfo.processInfo.environment["TZ"])
        if case .refused = verdict { unsetenv("TZ"); tzset() }
        return verdict
    }
}
```

## What stays out

- **Per-source skipping, musl, arm64, a per-distro Linux user:** as in the design's phase 1.
- **A switch for the Leaderboard per distro.** A distro that's on adds its days to the providers already shared; the switch in Settings → Tools in WSL is the one control, and the app says so once (*Decisions*, 2).
- **Days before `heldBefore`.** ClaudeBar's rule; no client change reaches them, and none is asked for (*Decisions*, 1).
- **Fresh `--logs-only` runs in the app's own uploads and the preview.** They read the kept days, at most one HUD cadence old while the distro runs (*Decisions*, 3).
- **Deleting kept days: a removed distro's before they leave the window, or all of them on leaving the Leaderboard.** They only age out; the file is a few hundred bytes a day (*Decisions*, 5).
- **A scratch distro on the PC, or fixture logs in a person's distro.** The numbers are proven in CI (*Decisions*, 4).
- **Reconciling kept days across a zone change.** Kept days hold labels, not records, so they can't be moved to the new zone's days; they're left out until the distro runs again (correction 8).
- **Settings' clock note for a distro whose zone isn't Windows'.** It goes: the days are Windows' zone's.
